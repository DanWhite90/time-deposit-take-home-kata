# XA Bank Time Deposit (Java)

Spring Boot 4 / Java 25 solution of the time deposit refactoring kata. It uses a hexagonal layout, PostgreSQL with
Flyway, an OpenAPI contract generated by springdoc, and Testcontainers for the integration tests.

## Run it

You need Docker. From this `java` folder:

```sh
./launcher.sh                                            # macOS / Linux
powershell -ExecutionPolicy Bypass -File .\launcher.ps1  # Windows
# or: docker compose up --build
```

Windows blocks local PowerShell scripts by default. `-ExecutionPolicy Bypass` allows this one run without changing
any system setting.

This builds the app image, starts PostgreSQL 16 and runs the Flyway migrations. The migrations create the
`timeDeposits` and `withdrawals` tables and load six sample plans. The app listens on `http://localhost:8080`.
Set `POSTGRES_PORT` if port 5432 is already taken on your machine.

Each `POST` changes the stored balances. To start again from the sample data, drop the database volume:

```sh
docker compose down -v
```

## Trigger the endpoints with Swagger

1. Open **http://localhost:8080/swagger-ui.html**. The raw contract is at `http://localhost:8080/v3/api-docs`.
2. Expand **time-deposits** → `GET /time-deposits` → **Try it out** → **Execute**. It returns every plan with its
   `id`, `planType`, `balance`, `days` and `withdrawals`.
3. Expand `POST /time-deposits/balances` → **Try it out** → **Execute**. It applies one month of interest to every
   plan, stores the new balances and returns the updated plans.
4. Run the `GET` again to see the stored balances.

The same calls with curl:

```sh
curl http://localhost:8080/time-deposits
curl -X POST http://localhost:8080/time-deposits/balances
```

These are the only two API endpoints. Swagger UI and `/v3/api-docs` serve the contract.

## Design

```
org.ikigaidigital
├── TimeDeposit, TimeDepositCalculator   original kata API, unchanged package and signatures
├── domain/model                         TimeDepositWithWithdrawals, Withdrawal (read model, BigDecimal money)
├── domain/interest                      InterestRateStrategy per plan + InterestRateStrategyFactory (no Spring)
├── application/port/in                  ListTimeDepositsUseCase, UpdateAllTimeDepositBalancesUseCase
├── application/port/out                 TimeDepositStore
├── application/service                  TimeDepositService (transactions)
├── config                               DomainConfiguration (registers domain classes as beans)
├── adapter/in/web                       TimeDepositController + record DTOs (OpenAPI annotations)
└── adapter/out/persistence              JPA entities, repository, TimeDepositPersistenceAdapter
```

- **No breaking changes.** `org.ikigaidigital.TimeDeposit` keeps its package, constructor and accessors. Its
  balance stays a `Double`. `org.ikigaidigital.TimeDepositCalculator` keeps its public no-arg constructor and
  `updateBalance(List<TimeDeposit>)`. Code written against the original kata compiles unchanged.
- **Same behavior.** The plan-specific `if` chain became one strategy per plan, picked by a factory. Adding a plan
  means one new strategy class and one factory case. `TimeDepositCalculatorCharacterizationTest` compares the
  refactored calculator with a verbatim copy of the original on 20,000 random deposits and requires bit-identical
  balances, because the assignment states the existing calculation is correct and must not change.
- **Known flaw, kept on purpose.** The original computes interest in `double`, and the strategies keep that
  arithmetic. An exact half-cent of interest can therefore round either way: a student balance of 45402.00 earns
  113.505, which `double` stores as 113.50499... and rounds down to 113.50. A balance plus interest sum can also be one
  binary digit off, e.g. 333595.64999999997 instead of 333595.65. Computing in `BigDecimal` would fix both. In the
  20,000-deposit sample that changes about 2,400 in-memory results, but only 4 stored balances, each by one cent.
  Because it changes existing results, it needs a business decision, so it is left as a follow-up.
- **Money.** The database stores `NUMERIC(19, 2)`; the read model and the API use `BigDecimal`. The interest
  calculation is the exception: it keeps the original `double` arithmetic and returns the interest, rounded to cents,
  as a `BigDecimal`, and `TimeDeposit.balance` stays `Double` as the assignment requires. The balance update therefore
  crosses the `TimeDepositStore` port as `Double`: `saveBalances` takes the calculator's `List<TimeDeposit>`. The
  adapter converts each balance straight back with `BigDecimal.valueOf(...)` at scale 2, which is exact for cent
  amounts up to about 10^13, far above any realistic deposit.

## Tests

```sh
mvn verify
```

Requires JDK 25+, Maven and a running Docker daemon: Testcontainers starts `postgres:16-alpine` for the persistence
and API tests. Unit tests cover each strategy, the factory, the calculator and the service.

GitHub Actions (`.github/workflows/java.yml` at the repository root) runs `mvn verify` and builds the Docker image
on every push to `main` and every pull request that touches `java/`.

## AI-assisted development

### Setup

- **Tool:** [Claude Code](https://claude.com/claude-code), used from IntelliJ IDEA through the official Claude Code
  plugin, with the Claude Opus 5.5 model with mixed efforts.
- **Rules:** [`AGENTS.md`](AGENTS.md) holds all project rules: the assignment constraints, code style, Spring and
  persistence conventions, the testing style, and running `mvn verify` before a task counts as done.
  [`CLAUDE.md`](CLAUDE.md) only imports it (`@AGENTS.md`), so Claude Code and any other agent that reads `AGENTS.md`
  follow the same rules.
- **Nothing else:** those two files are the whole agent configuration. There is no custom system prompt, hook, MCP
  server or subagent.

To reproduce the setup, install Claude Code and open this `java` folder in it, from the terminal or the IDE plugin. It
loads `CLAUDE.md`, and through it `AGENTS.md`, automatically. With JDK 25, Maven and Docker installed, it can run
`mvn verify` as the rules require.

### Workflow

I worked in small tasks: ask for one change, review the diff, have Claude run `mvn verify`, then commit. When I had to
correct a recurring mistake, I turned the correction into an `AGENTS.md` rule rather than repeating it, so the rules
grew with the project; the file's commit history shows each addition. Where a change involved a trade-off, such as
how to round interest, Claude laid out the options with evidence and I made the call.

### What was AI-assisted, and why

- **Boilerplate:** the Spring Boot, API, persistence and Docker Compose setup. Standard code, quick to check by running
  it.
- **Tests:** strategy, calculator, service, API, persistence and OpenAPI tests. Boundary cases get covered fast, and the
  tests check the generated code.
- **Behavior safety net:** the characterization test against a verbatim copy of the original calculator, which proves
  the refactor keeps every balance identical.
- **Precision analysis:** probes on 20,000 random deposits that found the original's half-cent rounding flaw (see
  Design). Hunting such edge cases by hand is slow.
- **Refactors I asked for:** the Spring-free domain package, the persistence adapter rename, the leaner balance update
  and the dead-code removal. Quick to do, and the tests catch regressions.
- **Style:** applying the `AGENTS.md` rules across the code. Repetitive, rule-based changes.
- **Reviews:** checks against the assignment and `AGENTS.md`, an end-to-end run and a build of every commit. A second
  reviewer that does not skip items.
- **Commit history:** splitting a large commit and fixing commits that did not compile, so every commit is atomic and
  builds.
- **Delivery:** Dockerfile layer caching, the non-root user and the GitHub Actions workflow. Standard practice that is
  easy to verify.
